# ADR-0003: Use Google Drive for Geospatial File Storage

**Status:** Accepted
**Date:** 2026-07-18

## Related documents
- architecture/01-system-overview.md
- architecture/04-data-model.md
- architecture/08-infrastructure-deployment.md

## Context
The system needs to store large geospatial files (.shp, .tiff) generated by survey teams. Supabase's free tier has strict storage limits (1GB) which would be quickly exhausted by these files. The team already uses Google Drive informally.

## Decision
**Use Google Drive for heavy storage:** The app will use the Google Drive API to upload files directly from the client. Supabase will only store the metadata (Drive URL, location, acquisition timestamp, zone).
- **Rationale:** Offloads heavy storage to an existing, high-capacity system the team already uses, preserving the Supabase free tier for structured data.
- **Alternatives:** Supabase Storage (too expensive/limited for free tier MVP), AWS S3 (adds infrastructure complexity and billing).
- **Reversibility:** Low. We can easily switch to S3 later by updating the metadata links and upload logic, but migrating existing files would take effort.

## Consequences
- **Easier:** Keeps infrastructure costs at zero. Leverages Google Workspace for folder access control.
- **Harder:** The app must integrate with the Google Drive API (OAuth/Service Accounts), which adds complexity to the file upload flow compared to native Supabase Storage.
